# بازبینی هزینه Kubernetes

وقتی یک مجموعه ابری یا Kubernetes را برای هزینه بازبینی می‌کنم، این ده سوال را از اول تا آخر می‌روم. قبض دیر می‌رسد. تا آن موقع تصمیم گران قبلاً در حال اجراست: node pool بزرگ‌تر از اوج واقعی، staging که آخر هفته هم روشن می‌ماند، دیسک جا مانده بعد از مهاجرت. علت در معماری و عادت است، نه در فاکتور.

سوال‌ها همان‌هایی است که در [Cloud cost is an engineering problem](https://shafie.dev/notes/cloud-cost-is-an-engineering-problem/) آمده. این‌جا کمی بازشان کرده‌ام تا معلوم باشد اسکریپت کدام را در کلاستر می‌بیند و کدام را نه.

۱. **می‌شود بخش عمده قبض را به یک تیم، یک سرویس و یک محیط نسبت داد؟**
اگر تیم و سرویس و محیط روی resource معلوم نباشد، قبض یک عدد است و از یک عدد فقط یک کار برمی‌آید: چیزی را قطع کردن. اسم namespace صاحب نمی‌سازد. اسکریپت هم صاحب نمی‌سازد.

۲. **هر ردیف درشت یک صاحب دارد که هزینه را بدون رفتن پیش مالی می‌بیند؟**
showback را قبل از بحث chargeback می‌خواهم. کسی رفتارش را عوض می‌کند که عدد را کنار سرویس خودش ببیند، نه در جدولی که هر فصل یک بار از راه می‌رسد. این را kubectl جواب نمی‌دهد.

۳. **محیط غیر production، از نظر اندازه و زمان روشن بودن، غیر production است یا تمام هفته مثل production بالا می‌ماند؟**
staging و dev و sandbox نباید از نظر اندازه مثل production باشند. شب و آخر هفته می‌توانند خواب باشند. اسکریپت namespaceهایی را نشان می‌دهد که از اسم‌شان غیر production هستند، ولی requestsشان در حد production است. زمان‌بندی را نمی‌بیند. آن را باید در Git یا در کنسول پیدا کرد.

۴. **دیسک وصل‌نشده، IP بی‌مصرف، LoadBalancer بیکار، snapshot قدیمی، یا کلاستر فراموش‌شده مانده است؟**
این‌ها همان اتلافی است که از دور دیده می‌شود. داخل همین کلاستر، اسکریپت LoadBalancer بدون backend آماده را می‌بیند. PV را اگر Available یا Released یا Failed باشد می‌آورد، و PVC را اگر Pending یا Lost باشد، یا Bound باشد ولی pod روشنی آن را mount نکرده باشد. IP و snapshot و یک کلاستر دوم در اکانت دیگر از دسترس kubectl خارج است.

۵. **requests و limits از روی مصرف دیده‌شده آمده‌اند، یا از یک template که محض احتیاط کپی شده؟**
request کپی‌شده را با نگاه اول نمی‌شود دید. اسکریپت container بدون request یا limit را می‌آورد، و موردی را که limit از request خیلی فاصله گرفته. اگر metrics باشد، workloadهایی را هم می‌آورد که requestشان از مصرف فاصله دارد. حدس، اندازه‌گیری نیست.

۶. **autoscaling همان‌قدر که scale out می‌کند، scale in هم می‌کند؟**
مقیاسی که فقط بزرگ می‌شود طراحی نیست. عادت است. تاریخچه‌اش در یک `kubectl get` نیست. باید خود scaler را دید.

۷. **data transfer یک عدد دیدنی است، و معلوم است کار کدام سرویس است؟**
ترافیک بین zone و خروج به اینترنت معمولاً روی هیچ نموداری نیست. اسکریپت قبض شبکه را نمی‌بیند.

۸. **قبل از خریدن ظرفیت reserved یا committed اندازه گرفته‌اید؟**
تعهد روی اندازه غلط، اتلاف را قفل می‌کند. اول مصرف باید راست باشد. این ابزار reservation پیشنهاد نمی‌کند.

۹. **برای کنترل هزینه، یک بررسی قابلیت اطمینان دارید؟ هدف چیست، و سر اوج بار چه می‌شود؟**
برای جمع‌وجور شدن گزارش، سرویس را تحت فشار نمی‌گذارم. headroom اگر برای هدف latency لازم است جزو طراحی است. ظرفیت اضافه دائمی، فقط چون به autoscaling اعتماد نیست، عادت است. قبل از برداشتن ظرفیت، هدف را در همان بحث بیاورید.

۱۰. **اندازه و زمان‌بندی مطلوب زیرساخت در Git است، یا فقط در کنسولی که پارسال باز بوده؟**
اگر infrastructure as code و GitOps دارید، desired state می‌تواند size و schedule و lifetime را هم داشته باشد، نه فقط یک YAML که همیشه روشن است. اسکریپت کلاستر زنده را می‌خواند، نه مخزنی که باید این را تعریف می‌کرد.

اگر دو سوال اول جواب ندارد، از همان‌جا شروع کنید. روی قبضی که توضیحش را ندارید، بهینه‌سازی یعنی حدس.

اسکریپت برای سوال‌های ۳ و ۴ و ۵ روی یک کلاستر به کار می‌آید و جای بقیه فهرست را نمی‌گیرد. ترتیبی که خودم در بازبینی استفاده می‌کنم: اول دیده شدن هزینه، بعد محیط غیر production که باید غیر production بماند، بعد rightsizing وقتی اندازه‌گیری هست، و ظرفیت reserved در آخر.
